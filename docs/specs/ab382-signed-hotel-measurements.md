# AB#382: signed approval for sealed hotel measurements

Status: proposal for engineering and security review. This PR changes no admission rule or public approval claim. The first implementation slice starts after the signed bytes and rollout order are agreed.

## Problem and source map

The public `approved-measurements.json` names hotels and measurements but has no signature. The console's current reader drops hotel names when it turns rows into measurement strings. Broker admission uses one `sealed_measurements` list for every hotel (`broker/main.go`, `broker/admission.go:checkAttestation`). The SNP report and binding are checked, but that proves the measured guest, not that the owner approved that build for that hotel. `room-kit/sealed/README.md` states this distinction under “Image approval.” A new release must bind the attested hotel identity to its approved measurement, be independently verifiable, and survive a reboot for historical receipts. The broker already allows multiple operator hotels on one SNP chip (`broker/admission.go`, “One miner hotel per chip”); the signed release must represent that live topology.

The repository has a separate signed policy registry for TEE boxes (`cathedral/policy_registry.py`, `docs/TEE_BOX_SERVICE.md`, “The measurement list”). It already specifies Ed25519 signatures under pinned owner keys, canonical bytes, monotonic releases, expiry and revocation. It is a design and code precedent. Its TEE box profile list is not currently the sealed hotel admission policy.

## Proposed contract

1. The owner issues a versioned signed release with a positive monotonic release number, UTC publication and validity times, signing key ID, and an exact map from **enrolled hotel ID** to one approved SNP chip ID and one or more approved 96-hex SNP measurements. The chip ID is the full 64-byte report field, encoded as 128 lowercase hex characters, not the shortened broker display ID. A hotel or chip ID missing from the release is refused. Duplicate hotel IDs, duplicate measurements within an entry, unknown critical fields, malformed IDs, an all-zero chip ID and an empty approved set are refused. Multiple operator hotels may name the same full chip ID because several guests run on one physical SNP host. Each hotel still has its own signed hotel ID and measurement set; the broker's separate one-admitted-miner-hotel-per-chip rule remains in force. Do not count signed hotel entries as distinct physical machines. A host replacement needs a new higher release that replaces the chip pin; the old chip stops admitting under that hotel ID at the cutover.
2. Sign canonical bytes using the registry's existing Ed25519 convention: canonical JSON of the document without `signature`, with sorted keys, ASCII escapes and no insignificant whitespace. The implementation must publish one golden byte vector and signature, and verify it in Python, Go and the customer verifier. Do not treat JSON key order in a network response as the signature input without canonicalization.
3. The broker pins the owner public key outside the fetched release and atomically persists both the verified release bytes and a durable high-water `(release, digest)`. It rejects unsigned, unknown-key, expired, future, older or same-number-different-digest releases. Enforce mode requires a durable state directory and an operator-pinned minimum release or initial `(release, digest)`; a missing or corrupt state file must not silently reset the high-water mark. A bad update leaves the last accepted release in place only until its own validity or freshness ceiling expires; then new sealed admissions refuse. A restart during a fetch outage may use the persisted release within that same window. No fallback to the global `sealed_measurements` list in enforce mode.
4. After checking REPORT_DATA, measurement, AMD chain and any miner TLS binding, the broker selects the signed entry by its **enrolled** hotel ID and requires the SNP-bound `binding.hotel` to equal that ID. The current Go `snpBinding` does not parse `hotel`, so this slice must add that field. The broker then compares the signed **full** chip ID to the report's CHIP_ID and the measurement to that entry's set; both must match on every admission and re-attestation. A mutable request name or the broker's shortened chip display ID must not select or satisfy policy. The boot-provided hotel name is host-controlled; its presence in REPORT_DATA proves what the guest declared, while the signed chip pin identifies the approved physical SNP machine. When two operator hotels share a chip, the name and chip pair does not cryptographically distinguish their guest instances; operator endpoint/configuration trust remains part of the admission boundary. Preserve the current miner TLS binding and one-miner-per-chip rule. Apply the same signed policy to operator and miner bootstrap, Escape nonce planting, and any direct path that currently checks `SealedMeasurements`.
5. Publish the signed release and the separately documented owner public-key fingerprint at a stable public URL. The console preserves the hotel ID and verifies the signature and release status before saying “approved.” Provide a standalone verifier with a pinned key for customers who need independent proof. A page served from the same site as the key cannot be presented as independent trust in that site.
6. At room creation, retain the accepted policy release number and digest with the attested binding and receipt evidence. Historical verification uses the archived signed release valid at that time, not today's mutable list. The evidence must also bind that release digest to this room's admission and preserve the full SNP report and AMD verification material for its binding. A release digest stored beside a receipt, or a binding without its SNP report, is insufficient to prove historical approval: the existing `room-kit/verify_receipts.py` intentionally labels archived sealed bindings without a report `NOT PROVEN`. A revoked build stops **new** admissions; old receipts remain verifiable as historical evidence only to the level their archived evidence supports.

## Recommended format and state decisions for review

- Use a separate `cathedral_sealed_hotels_v1` envelope with its own pinned owner key set, while reusing the existing policy registry's canonical JSON and Ed25519 signature convention. The current TEE registry has an exact top-level key set and profile schema (`cathedral/policy_registry.py`); adding hotel IDs and chip pins there would change its trust domain and every existing reader. Reject duplicate JSON keys before canonicalization and reject unknown fields in this new envelope. A key ID is only a selector among independently pinned keys; a key supplied by the fetched document grants no trust.
- Keep the active release and its high-water checkpoint in **one broker transaction** under `state_dir`, separate from the periodically saved `client-state.json`. Store the exact verified release bytes, release number, SHA-256 digest and acceptance time in a single durable record. A broker restart must reverify those bytes before using them. An update becomes active only after its record commits; a write failure leaves the previous release active and reports the update as failed. `broker/state.go` currently writes a temporary client-state file and renames it without a directory sync, so copying that path alone would not establish this policy's durability guarantee. An operator-pinned minimum release or `(release, digest)` outside the fetched release remains necessary to detect restoration of an older state directory; local transactionality cannot prevent a whole-disk rollback.
- Publish each accepted release as immutable signed bytes at a release-specific URL, with its digest, and retain the same bytes in the binding/receipt archive keyed by digest. The current public URL may point to the latest release, but historical verification must fetch the archived release by digest and verify its signature and validity at the receipt's admission time. The contract slice must define a verifiable admission record that binds room ID, SNP binding hash, report, release digest and admission time; a mutable broker row does not independently prove that relationship. Preserve the report and chain evidence needed to recheck the SNP binding after reboot. Do not infer historical approval from the current list or from a digest without the signed bytes.
- Make expiry and freshness independent checks: `valid_until` caps owner approval, while an operator-configured maximum age from `generated_at` caps stale delivery. Enforce mode refuses new admissions after either limit, including when fetch fails. The maximum age and rotation overlap require an operations decision based on the release cadence; leave them unset in the contract rather than inventing a safe number. Shadow mode may report the comparison without refusing admissions, but it must never label the unsigned list as signed approval.

## Work packages and rollout

1. **Contract and vectors:** approval binds both the enrolled hotel ID and the full SNP chip ID, per Eng's 14 Nov call. Settle whether this is a validated `sealed_hotels` extension of the existing signed registry or a separate envelope using its exact signing convention. Publish schema, key pin, golden vectors, expiry/freshness, bootstrap and state-corruption behavior, host-replacement cutover, rotation, revocation and historical rules. Define how a customer verifies the admission record's authenticity and time without trusting a mutable broker row. The remaining format, storage and admission-evidence choices are the decision gate for code.
2. **Publisher and verifier:** generate and verify releases from reviewed hotel/build inventory. The signing key stays out of GitHub and the public site. Add offline customer verification and cross-language positive/negative vectors.
3. **Broker shadow:** load and verify the release, persist high-water, and compare its per-hotel result with the current global list without changing admission. Count mismatches for every live hotel and direct sealed path.
4. **Broker enforce:** use the signed per-hotel result for every sealed admission and nonce path. Refuse missing/stale policy. Stage a release containing both old and new measured builds before each re-seal, observe all hotels, then remove old approvals in a later higher release.
5. **Public read and historical evidence:** publish the signed bytes, update the console to bind hotel and measurement, and archive releases or their verifiable bytes with room evidence. Test a receipt after a reboot and after a later revocation.

## Required tests and live proof

- Cross-language golden vector; changed hotel, measurement, release, validity, signature or key ID refuses. Unknown critical fields, duplicate entries, malformed hex, stale/future release and same-number equivocation refuse.
- Two operator hotels sharing one chip and measurement both pass when each matches its own signed hotel entry and enrolled endpoint. A hotel borrowing another hotel's measurement without its own approval, or presenting a binding hotel ID that differs from the enrolled ID, refuses even if the report and global list otherwise pass. A report with the correct hotel name and measurement but a different chip ID refuses; a shortened chip ID and an all-zero chip ID refuse. Two miner hotels on one chip cannot both be admitted, as under the existing broker rule. Re-attestation after a chip swap fails until a new signed release names the replacement.
- Operator admission, miner bootstrap, Escape nonce planting and re-attestation all use the signed per-hotel result. Policy fetch outage has a bounded stale window and then fails closed. Restart preserves high-water and accepted release; missing or corrupt state refuses in enforce mode, and rollback cannot restore an older approval. A guest reached at its own enrolled operator endpoint cannot select another hotel's entry merely by booting with that hotel's name.
- Re-seal overlap admits the old build only while the signed release lists it. After old build removal and hotel reboot, a receipt with the original policy digest and archived SNP proof can establish historical approval; a binding-only archive still reports `NOT PROVEN`.
- On a real SNP canary: read back the signed release and key pin, a positive attestation, a negative wrong-hotel policy check, a room receipt bound to the release, and const health before and after. Roll the remaining hotels only after canary evidence.

## Limits and dependencies

This does not sign the guest binary, change AMD certificate verification, cryptographically distinguish two operator guests on the same physical chip, or make the website an independent trust root. It depends on the archive work to retain historical releases. The signed format and the location of the durable broker high-water require engineering approval before implementation. No production policy or guest image changes are part of this spec PR.
