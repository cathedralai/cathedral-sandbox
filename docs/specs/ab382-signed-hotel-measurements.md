# AB#382: signed approval for sealed hotel measurements

Status: contract, with the four Eng/security decisions recorded on 16 Nov 2026 (see "Decisions (16 Nov 2026)"). This document changes no admission rule or public approval claim; implementation follows the work packages below.

## Problem and source map

The public `approved-measurements.json` names hotels and measurements but has no signature. The console's current reader drops hotel names when it turns rows into measurement strings. Broker admission uses one `sealed_measurements` list for every hotel (`broker/main.go`, `broker/admission.go:checkAttestation`). The SNP report and binding are checked, but that proves the measured guest, not that the owner approved that build for that hotel. `room-kit/sealed/README.md` states this distinction under “Image approval.” A new release must bind the attested hotel identity to its approved measurement, be independently verifiable, and survive a reboot for historical receipts. The broker already allows multiple operator hotels on one SNP chip (`broker/admission.go`, “One miner hotel per chip”); the signed release must represent that live topology. An operator hotel configured with `sealed_admission: off` currently bypasses `needsAttestation` and returns admitted without a check (`broker/admission.go:170-175,186-212`); `checkAttestation` can also return before the AMD chain check on that path (`broker/admission.go:297-299`).

The repository has a separate signed policy registry for TEE boxes (`cathedral/policy_registry.py`, `docs/TEE_BOX_SERVICE.md`, “The measurement list”). It already specifies Ed25519 signatures under pinned owner keys, canonical bytes, monotonic releases, expiry and revocation. It is a design and code precedent. Its TEE box profile list is not currently the sealed hotel admission policy.

## Contract

1. The owner issues a versioned signed release with a positive monotonic release number, UTC `generated_at`, `valid_from` and `valid_until` times, signing key ID, and an exact map from **enrolled hotel ID** to one approved SNP chip ID and one or more approved 96-hex SNP measurements. The chip ID is the full 64-byte report field, encoded as 128 lowercase hex characters, not the shortened broker display ID. A hotel or chip ID missing from the release is refused. Duplicate hotel IDs, duplicate measurements within an entry, unknown critical fields, malformed IDs, an all-zero chip ID and an empty approved set are refused. Multiple operator hotels may name the same full chip ID because several guests run on one physical SNP host. Each hotel still has its own signed hotel ID and measurement set; the broker's separate one-admitted-miner-hotel-per-chip rule remains in force. Do not count signed hotel entries as distinct physical machines. A host replacement needs a new higher release that replaces the chip pin; the old chip stops admitting under that hotel ID at the cutover.
2. Sign canonical bytes using the registry's existing Ed25519 convention: canonical JSON of the document without `signature`, with sorted keys, ASCII escapes and no insignificant whitespace. The implementation must publish one golden byte vector and signature, and verify it in Python, Go and the customer verifier. Do not treat JSON key order in a network response as the signature input without canonicalization.
3. Release state follows decision 1: the accepted envelope and its high-water mark live in guest-sealed state with a monotonic counter, and every rollback is refused. Owner public keys are pinned outside the fetched release, in the measured guest build and in broker configuration, each pin with its own `not_before` and `not_after` time so rotation (decision 2) needs no re-seal. Guest and broker reject unsigned, unknown-key, expired, future, too-old (decision 2), older or same-number-different-digest releases. Enforce mode requires an operator-pinned minimum release or initial `(release, digest)` in broker configuration; a missing, unreadable or corrupt sealed state never silently resets the high-water mark, because the broker's recorded per-hotel release still applies (decision 1). A bad update leaves the last accepted release in place only within the decision 3 window; after that, new sealed admissions refuse. No fallback to the global `sealed_measurements` list in enforce mode.
4. After checking REPORT_DATA, measurement, AMD chain and any miner TLS binding, the broker selects the signed entry by its **enrolled** hotel ID and requires the SNP-bound `binding.hotel` to equal that ID. The current Go `snpBinding` does not parse `hotel`, so this slice must add that field. The broker then compares the signed **full** chip ID to the report's CHIP_ID and the measurement to that entry's set; both must match on every admission and re-attestation. A mutable request name or the broker's shortened chip display ID must not select or satisfy policy. The boot-provided hotel name is host-controlled; its presence in REPORT_DATA proves what the guest declared, while the signed chip pin identifies the approved physical SNP machine. When two operator hotels share a chip, the name and chip pair does not cryptographically distinguish their guest instances; operator endpoint/configuration trust remains part of the admission boundary. Preserve the current miner TLS binding and one-miner-per-chip rule. Apply the same signed policy to operator and miner bootstrap, Escape nonce planting, and any direct path that currently checks `SealedMeasurements`. Enforce mode must reject an operator hotel's `sealed_admission: off` configuration before serving traffic: today `admitted()` returns true without attestation for that setting. The existing operational escape can remain available outside signed enforce mode, but it must never be represented as signed approval.
5. Publish the signed release and the separately documented owner public-key fingerprint at a stable public URL. The console preserves the hotel ID and verifies the signature and release status before saying "approved." Provide a standalone verifier with a pinned key for customers who need independent proof. A page served from the same site as the key cannot be presented as independent trust in that site.
6. At room creation, the guest puts the admission record of decision 4 inside the signed create receipt. Historical verification uses the archived signed release named by that record, not today's mutable list. The evidence must also preserve the full SNP report and AMD verification material for the binding whose key signed the receipt. A release digest stored beside a receipt, or a binding without its SNP report, is insufficient to prove historical approval: the existing `room-kit/verify_receipts.py` intentionally labels archived sealed bindings without a report `NOT PROVEN`. Removing a build from a higher release stops new admissions within the decision 3 bound; publication alone is not immediate revocation, and the emergency stop is a broker drain. Old receipts remain verifiable as historical evidence only to the level their archived evidence supports.

## Decisions (16 Nov 2026)

Eng/security decided the four open questions on 16 Nov 2026. These are binding for implementation; the rest of this document is consistent with them.

1. **Envelope and high-water state.** The release format is a separate `cathedral_sealed_hotels_v1` envelope with its own pinned owner key set, reusing the existing policy registry's canonical JSON and Ed25519 signature convention. The current TEE registry has an exact top-level key set and profile schema (`cathedral/policy_registry.py`); adding hotel IDs and chip pins there would change its trust domain and every existing reader. Duplicate JSON keys are rejected before canonicalization and unknown fields are rejected. A key ID is only a selector among independently pinned keys; a key supplied by the fetched document grants no trust.
   - The accepted envelope (exact verified bytes) and its high-water mark `(counter, release, digest)` are kept in **guest-sealed state**: written inside the sealed guest, encrypted and authenticated under a key derived from the SNP derived key (the key source in `docs/SEALED_DATA_VOLUME.md`, which binds the chip, measurement, guest policy and HOST_DATA; together the launch identity), so the host can neither read nor forge it. State is reverified (signature, schema, digest) on every load before use.
   - The counter is **monotonic**: sealed state carries a random 32-byte `state_id` chosen when the state is created, and a counter that starts at 1 for the first accepted release in that state, increases by exactly 1 with each newly accepted release, and is never reset or reused within that `state_id`. A newly accepted release must have a higher release number than the stored one. An update becomes active only after its sealed write commits; a write failure leaves the previous release active and reports the update as failed.
   - **Rollback is refused.** The guest refuses any release lower than its high-water and any same-number release with a different digest. Because the host can put back an older copy of a whole sealed disk (`docs/SEALED_DATA_VOLUME.md`, "Still not covered"), the guest proves its `(state_id, counter, release, digest)` on admission and re-attestation: the broker sends a fresh nonce, and the guest returns a new SNP report whose REPORT_DATA commits to that nonce and those values. Today's `POST /room/attest` puts caller-supplied bytes into REPORT_DATA verbatim and returns no sealed state (`room-kit/README.md`, "Fresh report over caller data"), so this slice must extend it or add a guest endpoint that does this. The broker refuses a hotel whose release is lower than the last release it recorded for that hotel or the operator-pinned minimum release. For the hotel's current chip ID and measurement it also records the last `(state_id, counter)` and refuses a lower counter under the same `state_id` (a restored older disk) and any different `state_id` (state deleted, cleared or replaced). The broker keeps this per-hotel record and its own current accepted release in durable state written with a directory sync (unlike today's `client-state.json` rename in `broker/state.go`); the pinned keys and pinned minimum stay in broker configuration. The state header names its launch identity, authenticated under the state key. A reboot with the same launch identity derives the same key, reads the same state and continues its counter. State whose header names a different launch identity (a re-seal, a host replacement or a relaunch with other HOST_DATA) cannot be read under the new key and is treated as absent, not corrupt. State whose header names the current launch identity but that fails authentication or schema or digest reverification is corrupt and the guest refuses to serve sealed rooms until an operator clears it. A stored release that verifies but whose signing key's pin window has since ended, or that is past its age or validity limits, is stale rather than corrupt: the guest keeps its `state_id` and counter and serves no new room until it accepts a fresh release. When sealed state is absent, the guest creates a new `state_id`, starts the counter at 1 and accepts a freshly fetched release. On a new measurement or a new chip ID (a re-seal or a host replacement, which derive a different key), the broker replaces its recorded `(state_id, counter)` for that hotel and admits the guest only if that release is at least the broker's recorded release for the hotel and the pinned minimum. On the same chip ID and measurement, the broker never accepts a new `state_id` by itself; recovery from deleted or cleared state there is an explicit, logged operator reset of that hotel's record, after which the same release rule applies. Losing, deleting or restoring state therefore cannot bring back an older approval.
2. **Freshness and rotation.** The maximum policy age is **24 hours** from `generated_at`. The owner therefore re-signs and publishes a release (a new release number) at least once every 24 hours, and should do so with margin. `valid_until` remains a separate hard limit; enforce mode refuses new sealed admissions after either limit. Key rotation overlap is **1 hour**: the incoming key is pinned in guest builds and broker configuration ahead of time with a `not_before` at the rotation start, and the outgoing key's pin carries a `not_after` exactly 1 hour after that `not_before`. Guest and broker accept a release only under a key whose pin window contains the verification time, so after the overlap a release signed only by the outgoing key is refused everywhere without a re-seal. A release must be re-signed by the incoming key before the overlap ends. The outgoing pin is dropped from the next guest build and broker configuration change.
3. **Revocation bound and emergency stop.** Revocation delay is **bounded at 5 minutes**. A broker fetches and verifies the published release at least once a minute and delivers each newly accepted release to every sealed hotel. A broker whose last successful fetch and verification is more than 5 minutes old, including during a fetch outage, refuses new sealed admissions and places no new room on a sealed hotel until a fetch succeeds; the 24 hour maximum age does not extend this bound. The broker places a room only on a hotel whose guest-sealed state holds the broker's current accepted release; a hotel still holding an older release gets no new room until it accepts the update. Release acceptance is monitored per broker and per hotel. The **emergency stop is immediate via broker drain**: an operator sets `drain: true` on each affected hotel (`PATCH /v1/broker/hotels/<id>`), and the broker places no new room there from that moment, without waiting for a release. Drain does not stop rooms already running; removing them is a separate operator action.
4. **Customer proof of admission.** The customer's proof is the **admission record inside the create receipt**. The sealed guest signs the create receipt with its receipt key, which is bound to its SNP report through the binding. The receipt carries an `admission` object with the policy `release` number, the policy `digest` (SHA-256 of the exact signed envelope bytes) and the admission `time` (UTC seconds). A customer verifies the receipt signature and chain, the binding and SNP report with its AMD chain, fetches the immutable signed release by that digest, verifies its signature under a published owner key whose pin window contained the admission time (retired keys stay published with their windows for this), checks that the attested hotel, chip ID and measurement are in that release, and checks that the time lies within the release's `valid_from` to `valid_until` and within 24 hours of its `generated_at`. Each accepted release is published as immutable signed bytes at a release-specific URL with its digest and retained in the receipt archive keyed by digest. The admission time is the sealed guest's clock; it is authenticated as what the guest signed, not as an independent timestamp. A mutable broker row is not proof.

Shadow mode may report the signed comparison without refusing admissions, but it must never label the unsigned list as signed approval.

## Work packages and rollout

1. **Contract and vectors:** approval binds both the enrolled hotel ID and the full SNP chip ID, per Eng's 14 Nov call, in the separate `cathedral_sealed_hotels_v1` envelope (decision 1). Publish schema, key pin, golden vectors, the 24 hour maximum age and 1 hour rotation overlap (decision 2), guest-sealed state layout and counter, bootstrap and state-corruption behavior, host-replacement cutover, the 5 minute revocation bound and drain procedure (decision 3), the create receipt `admission` fields (decision 4) and historical rules. Specify the enforce-mode rejection of operator `sealed_admission: off`.
2. **Publisher and verifier:** generate and verify releases from reviewed hotel/build inventory, re-signing at least every 24 hours. The signing key stays out of GitHub and the public site. Add offline customer verification of the create receipt admission record and cross-language positive/negative vectors.
3. **Guest state and broker shadow:** the guest verifies and keeps the release and counter in guest-sealed state and reports them in attested evidence; the broker records per-hotel high-water and compares its per-hotel result with the current global list without changing admission. Count mismatches for every live hotel and direct sealed path.
4. **Broker enforce:** use the signed per-hotel result for every sealed admission and nonce path. Refuse missing, stale (over 24 hours), rolled-back or unconfirmed (over 5 minutes since last successful fetch) policy. Stage a release containing both old and new measured builds before each re-seal, observe all hotels, then remove old approvals in a later higher release.
5. **Public read and historical evidence:** publish the signed bytes immutably by digest, update the console to bind hotel and measurement, add the `admission` record to the create receipt, and archive releases with room evidence. Test a receipt after a reboot and after a later revocation.

## Required tests and live proof

- Cross-language golden vector; changed hotel, measurement, release, validity, signature or key ID refuses. Unknown critical fields, duplicate entries, malformed hex, stale/future release and same-number equivocation refuse.
- Two operator hotels sharing one chip and measurement both pass when each matches its own signed hotel entry and enrolled endpoint. A hotel borrowing another hotel's measurement without its own approval, or presenting a binding hotel ID that differs from the enrolled ID, refuses even if the report and global list otherwise pass. A report with the correct hotel name and measurement but a different chip ID refuses; a shortened chip ID and an all-zero chip ID refuse. Two miner hotels on one chip cannot both be admitted, as under the existing broker rule. Re-attestation after a chip swap fails until a new signed release names the replacement.
- Operator admission, miner bootstrap, Escape nonce planting and re-attestation all use the signed per-hotel result. In enforce mode, config load refuses an operator hotel with `sealed_admission: off` even when its signed entry exists; in non-enforce mode the existing operational escape still cannot be labelled signed-approved. If a higher release removes a build while a broker's fetch is unavailable, that broker refuses new sealed admissions and placements once its last successful fetch is more than 5 minutes old, even though the cached release is within 24 hours. Once the higher release is accepted, the removed build refuses immediately on that broker. Draining an affected hotel stops new placements on it immediately with no release change, and its existing rooms keep running. A release older than 24 hours, past `valid_until`, or signed only by an outgoing key more than 1 hour after rotation refuses. Guest reboot of the same build on the same chip preserves the sealed release and counter. Corrupt sealed state refuses in enforce mode. After a re-seal or host replacement, absent sealed state restarts the counter at 1 and is admitted only on a release at least the broker's recorded one and the pinned minimum. On the same chip ID and measurement, deleted or cleared state (a new `state_id`) refuses until an operator resets that hotel's record, then the same release rule applies. A lower release, a same-number different-digest release, or a restored older sealed state (release below the broker's recorded release or the pinned minimum, a lower counter under the recorded `state_id`, or a different `state_id` on the same chip ID and measurement without an operator reset) refuses. A guest reached at its own enrolled operator endpoint cannot select another hotel's entry merely by booting with that hotel's name.
- Re-seal overlap admits the old build only while the broker's accepted active signed release lists it. After old build removal and hotel reboot, a create receipt whose `admission` record names the original policy release, digest and time, with archived SNP proof and the archived signed release, establishes historical approval; a changed digest, a time outside the release window or a binding-only archive reports `NOT PROVEN`.
- On a real SNP canary: read back the signed release and key pin, a positive attestation, a negative wrong-hotel policy check, a create receipt whose `admission` record names the accepted release digest and time, a drain that stops new placements at once, and const health before and after. Roll the remaining hotels only after canary evidence.

## Limits and dependencies

This does not sign the guest binary, change AMD certificate verification, cryptographically distinguish two operator guests on the same physical chip, or make the website an independent trust root. It depends on the archive work to retain historical releases. The admission time in a create receipt is the sealed guest's clock, not an independent timestamp. A drain does not stop rooms already running. No production policy or guest image changes are part of this spec PR.
